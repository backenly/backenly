# Signup abuse defence

## What was actually happening

Backenly was collecting signups like these:

```
nehafic171@aganseo.com
backenly.com@gravik.org
neliyit144@dysonc.com
mrej6qi3ucj1@cropimg.com
```

The intuitive read is "temp-mail services got past the blocklist, so grow the
blocklist." That read is wrong, and it was worth disproving before building
anything. Three measurements:

| Hypothesis | Result |
| --- | --- |
| They are known disposable domains | A **121,570-entry** disposable-domain list matched **0 of 4** |
| They are dead domains with no mail | **All 4** publish valid MX records |
| They are freshly registered throwaways | `aganseo.com` is **13 years old**, `gravik.org` is **17** |

No domain-shaped control would have stopped these, and a domain-age heuristic
would have false-positived on legitimate new startups while still missing two of
the four.

The property they actually share is that **a script filled the form**.
`backenly.com@gravik.org` is the proof: the local part is our own hostname,
which is what a form-filler emits when it templates the target site into an
email field. The others are generator output — `mrej6qi3ucj1` is base36,
`nehafic171` and `neliyit144` are the nonsense-word-plus-digits shape.

So the control that matters is proof-of-humanity, not domain reputation.

## Why not an allowlist of "credible" domains

Because the customers who pay are the ones on their own company domains.
Restricting signup to Gmail/Outlook/etc. would turn away exactly the segment
Backenly is built for while doing nothing about `<burner-account>@<major-provider>`.
Domain trust is a supporting signal here, never the gate.

## The layers

Ordered by how much work each one actually does.

### 1. Turnstile — `lib/auth/bot-defense.ts`

Cloudflare Turnstile on the email signup form, verified server-side. Free, no
request ceiling, invisible for most real users, no ad-graph coupling. This is
what stops the four addresses above, and the fifth one next week on a domain
nobody has seen yet.

Inert until configured — the widget does not render without
`NEXT_PUBLIC_TURNSTILE_SITE_KEY` and the server does not enforce without
`TURNSTILE_SECRET_KEY`. **Both must be set for the gate to close.**

If Cloudflare is unreachable it fails **open** and records a
`bot_defense_degraded` SecurityEvent. A captcha outage taking down all signups
is a worse failure than a few hours of unfiltered ones, and the layers below
still apply.

OAuth signups skip this: Google and GitHub already did the humanity check.

### 2. Rate limiting — `app/api/auth/register/route.ts`

10 signups per IP per hour. The policy already existed in `AUTH_LIMITS.signup`
but **the register route never consumed it**, so a script could register
unlimited accounts from one address at full speed. Now it does, and a trip
records `signup_rate_limited`.

### 3. Email trust — `lib/auth/email-trust.ts`

Server-side scoring, 0–100, returning a verdict rather than a boolean:

- **deny** — refuse the signup.
- **challenge** — allow it, but mark the account `untrusted`.
- **allow** — normal.

Hard fails: the classic disposable list (all 121k of them, so the easy cases
cost nothing), reserved domains, burner local parts, a local part that is our
own brand, and domains with neither MX nor an address record.

Contributing signals: unknown domain (+20), catch-all forwarder MX (+30),
MX host already blocklisted by the operator (+40), random local part (+35),
generator-shaped local part (+25), implicit-MX-only (+25). Credits: recognised
mailbox provider (−20), academic/government domain (−20).

Two design choices worth keeping:

- **The mailbox-provider credit is the main false-positive guard.** Real users
  in the database — `sandranair1661@`, `adhuadarshzz1@`, `yingquan526@` — look
  machine-generated by shape. On Gmail that tells you nothing, because Google
  already did the identity work. Shape signals must never convict alone.
- **`unknown_domain` is only 20 points**, well below the challenge threshold, so
  a founder on a two-week-old company domain sails through.

Measured behaviour on the real addresses (MX resolution on):

```
backenly.com@gravik.org      DENY       100  brand_in_local_part
mrej6qi3ucj1@cropimg.com     DENY        85  unknown_domain, catchall_forwarder_mx, random_local_part
nehafic171@aganseo.com       CHALLENGE   45  unknown_domain, generated_local_part
neliyit144@dysonc.com        CHALLENGE   45  unknown_domain, generated_local_part
<ordinary-mailbox>@<major-provider>  ALLOW   0  major_provider
<founder>@<university.ac.kr>        ALLOW  15  institutional_domain
```

The two ALLOW rows are redacted because they were real mailboxes belonging to
real people, and this repository is public. The abuse addresses above them are
left intact: those are attacker-controlled disposable domains, which is the
subject matter, not somebody's inbox. The scores and reason codes are the
measured ones either way — what the redaction removes is an identity, not a
result.

DNS is capped at 2.5 s with a 6-hour cache, and a resolver timeout is scored as
**unknown, never as bad** — our infrastructure problem must not lock out a real
user.

`Blocklist` rows with `kind: 'mx'` block every domain routing through that host.
Domain farms reuse mail infrastructure (`dysonc.com` routes through
`mail.wabblywabble.com`), so blocking one entry retires the whole farm instead
of playing whack-a-mole.

### 4. Account standing — `lib/auth/account-standing.ts`

This is the structural layer, and the one that does not depend on correctly
identifying an abusive domain.

An `untrusted` account can sign in and look around but **provisions nothing** —
no projects — until it verifies its mailbox. That inverts the economics:
minting an account stops being free value, whether or not any heuristic fired.

Two deliberate properties:

- Only `untrusted` accounts are gated. Every pre-existing user and every clean
  signup is unaffected, so this shipped without a migration window.
- Verifying the mailbox **promotes** the account, so a real person caught by a
  heuristic clears it themselves in one click, with no support round-trip.

### 5. Reaper — `app/api/cron/reap-abandoned-signups`

Daily sweep. Deletes an account only when **every** one of these holds: never
verified, flagged `untrusted` at signup, older than the grace window (14 days),
owns no projects, holds no API keys, has never made a request, and never signed
back in. Anything else is kept — deleting one real account costs far more than
leaving a dead row in the table. Capped at 200 per run.

Accounts predating the trust columns default to `trusted`, so the reaper cannot
reach back and delete anyone who signed up before the gate existed.

Run `?dryRun=1` first. It changes nothing and shows exactly what would go.

### 6. Admin visibility — `app/admin`

The Users tab gained a signup filter (All / Real users / Flagged / Unverified)
and an inline flag carrying the score and reason codes on hover. A clean
verified account shows no marker, so a flag means something.

## A bypass found and closed along the way

`GET|POST /api/users` was behind `requireAuth`, meaning **any authenticated
user** could call it. `GET` returned every account on the platform (an email
dump); `POST` created accounts with a caller-supplied `emailVerified` flag,
bypassing Turnstile, rate limits, and trust scoring entirely. One throwaway
account was enough to mint unlimited pre-verified ones.

Both handlers now require founder/admin, and `POST` runs the same trust engine
as the public path. Nothing in the codebase called either handler, so no caller
broke.

## Turning it on

1. **Cloudflare dashboard → Turnstile → Add site.** Widget mode *Managed*.
   Add `backenly.com` **and** `localhost` to the hostname list, or local signup
   will fail.
2. Set on the server:
   ```
   NEXT_PUBLIC_TURNSTILE_SITE_KEY=0x4AAA...
   TURNSTILE_SECRET_KEY=0x4AAA...
   ```
   `NEXT_PUBLIC_*` is inlined at build time, so this needs a **rebuild**, not
   just a restart.
3. Schema: **nothing to run by hand.** `scripts/deploy.sh` calls `npm run
   db:push` unconditionally on every deploy, so the four new `users` columns
   land automatically. They are additive with defaults, so the push is
   non-destructive.

   `prisma/migrations/add_signup_trust.sql` is the equivalent statements for
   reference and for anyone applying the change outside the deploy script.
   Note `/prisma/migrations` is gitignored, so that file is local-only and
   never reaches the server — the deploy does not depend on it.
4. Schedule the reaper. `vercel.json` carries the cron entry, but **crons in
   `vercel.json` do not fire on Hetzner** — add a crontab line on the box:
   ```
   30 4 * * * curl -s -H "x-cron-secret: $CRON_SECRET" https://backenly.com/api/cron/reap-abandoned-signups
   ```

## Tuning

`tests/auth/email-trust.test.ts` pins the thresholds against both real users and
the known-abusive addresses. If you adjust a weight, that suite is what tells
you whether you just started rejecting customers. Add any new false positive to
the `legitimate` list **before** changing a number.
